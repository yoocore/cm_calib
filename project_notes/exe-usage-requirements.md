# EXE 使用步骤需求文档

## 1. 文档目的

本文档用于定义本项目本地单用户 EXE 控制台的一期需求。

本文档的主要用途不是描述代码实现，而是明确以下内容：

1. 用户如何一步步使用该 EXE
2. 每个功能按钮和界面的行为是什么
3. 成功、失败、异常时系统应该如何表现
4. 哪些功能属于一期必须实现，哪些功能暂不实现

后续开发应优先以本文档为准，再决定具体代码结构和技术实现。

## 2. 产品目标

本 EXE 是一个运行在本机 Windows 上的单用户标定控制台。

它的目标是把当前已有的本地控制能力整合为一个可视化操作入口，使用户不需要频繁手动拼接命令行，即可完成以下事情：

1. 探测当前 CarMaker、IPG-MOVIE、DDE 的运行状态
2. 让运行环境进入可执行标定的就绪状态
3. 选择配置并启动一次标定任务
4. 在标定过程中查看实时日志和任务状态
5. 在标定结束后查看结果摘要和输出目录

## 3. 产品定位

本产品是本地 EXE GUI，不是 Web GUI。

一期产品的定位如下：

1. 主控层为本地 EXE GUI
2. 底层仍复用现有 Python CLI 脚本
3. 不要求远程访问
4. 不要求多用户共享
5. 不要求浏览器访问

## 4. 目标用户

目标用户是当前项目的本机操作者，即会使用 CarMaker、IPG-MOVIE、camera calibration 配置文件，并需要反复执行以下流程的人：

1. 检查当前运行环境是否正确
2. 选择目标 TestRun 和 camera 配置
3. 准备运行环境
4. 启动或停止一次标定
5. 查看结果和排错信息

## 5. 一期范围

一期必须实现的范围如下：

1. 运行态探测
2. Prepare Runtime
3. 启动标定任务
4. 停止标定任务
5. 日志实时显示
6. 结果摘要显示
7. 输出目录快捷打开

一期暂不实现的范围如下：

1. 多任务并行运行
2. 多用户共享
3. 远程 Web 访问
4. 历史任务图表分析
5. 在 GUI 内直接编辑复杂 JSON 参数
6. 在 GUI 内直接替代现有标定算法

## 6. 依赖前提

用户在使用 EXE 前，应满足以下前提：

1. 本机已安装可用的 CarMaker
2. 本机存在当前项目工作区
3. 当前项目所需 Python 环境可用
4. 当前项目底层控制脚本可运行
5. DDE 相关依赖可用

若前提不满足，EXE 不需要自动修复所有环境问题，但必须尽量给出清晰提示。

## 7. 一期界面总览

一期界面采用单窗口三栏布局。

### 7.1 左栏：Runtime

左栏用于选择 CarMaker 工程，并展示当前工程下 TestRun、Vehicle 和 camera sensor 的静态信息。

应显示以下信息：
上方应包含以下输入项：
1. 配置 CarMaker 工程目录（projectdir），提供打开按钮，让用户能够选择或修改当前工程目录
2. TestRun 名称或路径，提供打开按钮，让用户能够选择或修改

下方应包含以下信息：
1. 当前 Vehicle
2. 显示配置的所有camera sensor，其中active的sensor要高亮显示

### 7.2 中栏：Calibration

中栏用于配置标定信息，并提供环境准备相关操作，展示前置准备状态。

应包含以下内容：

1. 选择要标定的Camera，提供下拉选项进行勾选多个 camera。其右侧有一个检查按钮，用于检查当前选择的 camera 是否满足标定前提条件：是否具备原始图像，标注的原始图像，标注图像中的标注名称是否都涵盖在bootstrap-template.json中。
2. 在其下方显示所有被勾选的camera，并在每个camera后面有一个状态框，如果检查通过，要显示绿色对勾，否则显示红色叉号。放在叉号上，显示错误信息。
3. campaign rounds，explore的direction方向数量，explore的iter次数，refine的iter次数。要能看出来是层级关系，比如explore和refine是round的子集，explore下有direction和iter两个层级。预估耗时。
4. CM Prepare，在其后有一个下拉复选框，能从中选择系统中不同版本的CarMaker
5. Calib Start
6. Calib Stop
7. Status

### 7.3 右栏：Output

右栏用于显示当前任务日志和结果摘要。

应显示以下信息：

1. 当前输出目录，提供打开按钮，让用户能够直接打开当前输出目录
2. 实时日志，提供打开按钮，让用户能够直接打开
3. 单个结果区域按 camera 分块显示本次任务结果；每个 camera 都要独立显示自己的 best score、score 视图、overlap 视图、当前 iter score

## 8. 全局状态机

GUI 内部应至少维护以下状态：

1. idle：尚未检查运行态
2. preparing:正在准备运行态
3. passive:标定运行态未满足
4. ready：运行态满足启动标定的前提
5. running：标定任务正在运行
6. finished：标定任务已结束且结果可读取
7. failed：标定任务已结束但失败或结果不完整

不同状态下，按钮的可用性应受控，不应允许无效操作。

## 9. 典型用户流程

### 9.1 选择CarMaker
用户步骤：

1. 左栏选择 CarMaker 工程目录
2. 左栏选择 TestRun

系统步骤：

1. 读取当前目标工程目录
2. 读取当前 TestRun
3. 读取当前 Vehicle
4. 读取当前所有 camera sensor

成功结果：
1. 在左栏显示当前 Vehicle
2. 在左栏显示当前所有 camera sensor，其中 active 的 sensor 要高亮显示

注意事项：

1. 左栏高亮跟随对应 Vehicle 文件中被激活的 sensor
2. 左栏显示的是静态文件状态，不依赖真实运行态探测

3. 在这个过程中，仅是静态读取，无需真正打开 CarMaker 及 IPG-MOVIE

### 9.2 标定前置文件检查
用户步骤：
1. 中栏选择要标定的Camera
2. 点击中栏检查按钮

系统步骤：

1. 检查选择的 camera 是否满足标定前提条件：是否具备原始图像，标注的原始图像，标注图像中的标注名称是否都涵盖在 bootstrap-template.json 中。
2. 检查原始图像文件名和标注图像文件名是否包含对应 Vehicle 中的 sensor 名称。
3. 原始图像和标注图像统一从当前 projectdir 下的 Movie 目录中检索，并按对应 sensor 名称匹配相关文件。

成功结果：
1. 在中栏显示所有被选择的 camera 是否满足标定前提条件

失败结果：
1. 若原始图像或标注图像文件名中未包含对应 sensor 名称，则在“标定前置文件检查”中报错，并明确指出具体 camera、具体文件名和缺失的 sensor 名称


### 9.3 标定配置
用户步骤：
1. 中栏设置campaign rounds
2. 中栏设置explore的direction方向数量，explore的iter次数（要有默认填充的配置）
3. 中栏设置refine的iter次数（要有默认填充的配置）

系统步骤：

1. 更改脚本输入参数的相关值

注意事项：
上述配置仅是对一个摄像头的配置，所有摄像头一样

成功结果：
1. 在中栏显示上述配置的预估时间，这个时间会随上述配置的修改而变化

### 9.4 标定准备
用户步骤：
1. 中栏点击CM Prepare按钮

系统步骤：

1. 关闭已有的 CarMaker 进程、GUI IPG-MOVIE 进程、GPUSensor 进程
2. 根据已选择的camera，为每个摄像头在脚本代码目录下的 config 文件夹中生成 camera.xxx.json 文件；若同名 json 文件已存在，则先备份旧文件，再生成新的 json 文件。
3. 根据中栏CM Prepare按钮后面的复选框内容，打开对应版本的CarMaker
4. 根据左栏的projectdir，切换到对应工程目录
5. 根据左栏的testrun，切换到对应TestRun
6. start testrun等待处于running状态后stop testrun
7. 打开ipgmoive，等待画面加载完成
8. 切换ipgmoive-view-show-ABRAXAS，使其处于被勾选
9. 切换 ipgmoive-camera-sensor-xxxx，使其处于被勾选
10. 设置ipgmoive-view-size-custom中的尺寸，使其与真实图片的尺寸一致
11. 打开ipgmoive-camera-settings
12. 打开ipgmoive-camara lens parameters
13. 执行DDE健康检查

注意事项：

1. 当 Vehicle 文件中仅 active 了一个摄像头时，IPG-MOVIE 中只有一个 camera sensor 可选项，因此不会选错

成功结果：
1. 未点击prepare之前，status: idle
2. 点击prepare之后，但环境准备中，status: preparing
3. 点击prepare之后，但环境准备失败，status: passive，在下方增加文本框显示失败原因
4. 点击prepare之后，环境准备成功，status: ready

### 9.5 启动标定
用户步骤：
1. 确认运行态已 ready
2. 确认配置文件和运行参数
3. 中栏点击 Calib Start按钮

系统步骤：

1. 锁定当前输入项，避免任务运行中被修改。如果运行过程中用户点击左栏的配置，则弹出警告提示用户当前任务正在运行，需要先停止标定任务。
2. 生成本次任务标识
3. 在 ready 状态下点击 Calib Start 时，直接启动底层标定脚本，不重复执行 CM Prepare
4. 实时接收 stdout 和 stderr
5. 将日志持续显示到右栏
6. 实时读取结果文件，按 camera 提取并刷新结果摘要；每个 camera 都要独立显示自己的 best score、score 视图、overlap 视图、当前 iter score

注意事项：
标定脚本在执行第一个摄像头标定的时候，环境准备工作已经被CM Prepare 步骤准备好，但是后续摄像头的标定需要执行一些特殊的步骤（因为涉及到配置的更改及CarMaker的运行等），需要在标定脚本中实现：
1.假设在“标定前置文件检查”阶段，被勾选的摄像头的名称会以文本的形式保存下来，其表示了本次标定涉及的摄像头，在启动标定时，需要将这些摄像头的名称传递给底层脚本。
2. 在底层脚本中，将该文本作为参数输入。点击 Calib Start 时，应跳过 CM Prepare，直接继续执行标定流程。
1. 在执行完第一个摄像头的标定后，根据下一次要执行的摄像头名称，更改CarMaker的配置文件（testrun所使用的vehicle文件），仅active被执行的摄像头，然后start testrun等待处于running状态后stop testrun，切换ipgmoive-camera-sensor-xxxx，使其处于被勾选，执行健康检查，再运行实质标定。以此循环，直到所有摄像头标定完成。


成功结果：

1. 标定过程中,中栏status: running
2. 标定完成,中栏status: finished

失败结果：

1. 标定失败，中栏status: failed
2. 在下方增加文本框显示退出失败或结果缺失的原因
3. 日志保留以便排查

### 9.6 停止标定

用户步骤：

1. 在 中栏status:running 状态下点击“calib stop”

系统步骤：

1. 向底层任务发送停止请求，结束底层脚本，保留CarMaker 和 GUI Movie
2. 等待子进程退出或进入可安全停止状态
3. 刷新界面状态

成功结果：

1. 标定任务终止
2. 日志中记录停止动作
3. 若存在部分结果，可按可读取程度显示摘要
4. Stop 之后再次点击 Start 时，从头开始执行本次被勾选 camera 的标定流程

失败结果：

1. 明确提示停止失败
2. 保留日志和当前任务状态

## 10. 关键口径

本节用于收口当前已经明确的关键实现口径。后续开发应以本节定义为准，避免行为偏差。

### 10.1 Camera 列表来源

当前需要明确中栏“选择要标定的 Camera”列表的来源。

确定口径：

1. Camera 列表仅来自当前 Vehicle 的 camera sensor 列表

### 10.2 多 Camera 执行顺序

当前需要明确被勾选的多个 camera 在一次任务中的执行顺序。

确定口径：

1. 默认按 camera 名称顺序执行
2. GUI 允许用户手动拖拽调整执行顺序
3. 若用户未手动调整，则使用默认名称顺序

### 10.3 CM Prepare 成功判定

当前需要明确 CM Prepare 的成功标准。

确定口径：

1. 必须成功打开 Camera Settings 和 Lens Parameters，才算 Prepare 成功
2. 任何一个未成功打开，Prepare 都应判定为失败
3. Prepare 失败时，中栏 status 进入 passive，并显示失败原因

### 10.4 预估耗时口径

当前需要明确中栏“预估耗时”的统计口径。

确定口径：

1. 显示当前所有被勾选 camera 的总预计耗时
2. 该总预计耗时不包含一次性 CM Prepare 时间
3. 该时间用于辅助预估，不承诺严格精确

### 10.5 右栏结果主语义

当前需要明确右栏结果区域在多 camera 任务中的主要显示对象。

确定口径：

1. 右栏先做成一个统一结果区域，而不是为整个任务只显示一套混合结果
2. 该结果区域内部需要按 camera 分块显示结果，每个 camera 都要独立展示自己的 best score、score 视图、overlap 视图、当前 iter score
3. 不允许把多个 camera 的 best score、score 视图、overlap 视图、当前 iter score 混成一套任务级汇总结果
4. 若后续实践证明单个结果区域内的分块展示仍不够清晰，再拆分为多个结果区

### 10.6 Stop 后再次 Start 的行为

当前需要明确点击 Calib Stop 后，再次点击 Calib Start 的默认行为。

已知条件：

1. Calib Stop 后保留 CarMaker 和 GUI Movie
2. Calib Start 不重复执行 CM Prepare

确定口径：

1. 再次 Start 时，跳过 CM Prepare，直接进入标定流程
2. 再次 Start 时，从头开始执行本次被勾选 camera 的标定流程
3. 一期不弹出二次选择框
4. 若当前环境不健康，则应重新进入准备流程后才能再次启动

### 10.7 单实例处理的精确规则

当前需要把“按规则处理”展开成更明确的决策口径。

确定口径：

1. 按当前 EXE 设计，CM Prepare 总是先关闭已有的 CarMaker、GUI IPG-MOVIE、GPUSensor 相关进程，再启动目标版本的 CarMaker
2. 因此一期 EXE 主流程中不依赖“单实例复用后再判断是否工程不匹配”的分支
3. 一期 EXE 以“清空现有环境后重新建立目标环境”为标准准备策略
4. 若后续版本需要支持保留外部现有实例复用，再单独补充更细的单实例复用决策规则

### 10.8 左栏静态读取与运行态读取的边界

当前需要明确左栏“静态读取”与后续“运行态读取”的边界。

已知文档要求：

1. 左栏选择 projectdir 与 TestRun 时，无需真正打开 CarMaker 和 IPG-MOVIE
2. CM Prepare 后才进入真实运行态

确定口径：

1. 左栏阶段只允许读取文件系统中的静态信息
2. 左栏阶段不允许任何 DDE 读取或进程级运行态探测
3. 左栏阶段不对现有运行中的 CarMaker 或 IPG-MOVIE 提供运行态提示信息
4. 所有真实运行态检查统一放到 CM Prepare 或后续标定阶段
5. 左栏中 active sensor 的高亮仅跟随对应 Vehicle 文件中的激活状态
6. 左栏静态信息默认按 1 秒周期刷新；若实现验证表明该频率过快或不稳定，可放宽为每 3 到 5 秒刷新一次

## 11. 异常场景要求
### 11.1 DDE 相关

必须覆盖以下场景：

1. DDE 不可连接
2. DDE 健康检查失败
3. 可连接但无法读取运行态

### 11.2 配置与结果相关

必须覆盖以下场景：

1. 配置文件不存在
2. 配置文件格式错误
3. camera sensor 不存在
4. 结果文件不存在
5. 结果文件存在但内容不完整

## 12. 交互与提示要求

界面提示应满足以下要求：

1. 不只告诉用户失败，要告诉用户失败在哪一步
2. 日志区应保留完整原始输出
3. 状态区应给出概括性结论
4. 对可重试的错误，应允许用户直接再次点击相关按钮
5. 对不可安全重复的操作，应在运行中禁用按钮

## 13. 一期验收标准

一期开发完成后，至少应满足以下验收标准：

1. 用户可以在 GUI 中看到当前运行态
2. 用户可以在 GUI 中执行 CM Prepare
3. 当 CarMaker 工程不匹配时，系统能识别并按规则处理
4. 用户可以从 GUI 启动一次标定任务
5. 用户可以在 GUI 中查看实时日志
6. 标定过程及结束后 GUI 能显示结果摘要
7. 用户可以打开输出目录
8. 常见失败场景下 GUI 能给出明确提示

## 14. 后续可扩展项

以下内容不属于一期必须实现，但可以作为后续扩展方向：

1. 历史任务列表
2. 结果趋势图
3. 参数 diff 对比
4. 本地只读 Web dashboard

## 15. 文档修改约定

本文档是后续 EXE 开发的需求输入文档。

建议后续修改时遵循以下原则：

1. 优先改“用户要看到什么、点什么、系统做什么”
2. 尽量少写底层技术实现细节
3. 如果有新的边界条件，优先补到“异常场景要求”
4. 如果有新的按钮或新流程，优先补到“典型用户流程”和“功能明细”

# Autonomous Fix Loop — Camera Calibration Project

## 核心理念

**不要只改代码，要自闭环。** 用户给出问题后，你应该：执行 → 捕获输出 → 分析 → 修复 → 验证，循环直到成功或达到上限。

将用户从「手动执行 → 贴错误 → 等你改 → 再执行」的循环中解放出来。

---

## 工作流

### 第0步：理解需求

用户明确说出要修什么（如"FBO 又失败了"、"测试挂了"、"标定流程卡住了"）。如果需求模糊，先问清楚。

### 第1步：选择执行模式

根据问题的性质，判断能否完全自主执行：

| 模式 | 条件 | 策略 |
|------|------|------|
| **完全自主** | 不依赖 CarMaker/IPG-MOVIE 运行，仅涉及 Python 级别代码/测试 | 自我闭环：执行→捕获→分析→修复→验证，不打扰用户 |
| **半自主** | 需要 CarMaker/IPG-MOVIE 运行环境（DDE/Tcl 通信） | 修改代码 + 嵌入诊断 + 准备执行命令 → 告知用户执行并反馈结果 → 收到反馈后继续 |

**完全自主可执行的内容（参考）：**
- `python -m pytest tests/test_persistent_counters.py -v`
- `python -m pytest tests/test_cmapi_testrun_control.py -v`
- `python -m pytest tests/ -k "not dde and not fbo_after_prepare" -v`
- `python <script>.py` —— 读取脚本内容判断是否依赖 CarMaker

**半自主需要用户执行的内容：**
- `python camera_calibration.py --capture` 等实际标定命令
- `python calibration_orchestrator.py`
- `python dde_health_check.py`（需要 DDE 连接）
- 任何涉及 `dde` 或 `Tcl_Eval` 的脚本

### 第2步：初始诊断

**完全自主模式：** 直接执行相关命令，捕获输出。使用 `bash` 运行命令，仔细分析 stdout/stderr/return code。

**半自主模式：** 
1. 在修复的代码中嵌入诊断输出（如 `DIAG_*` 变量或日志）
2. 准备让用户执行的精确命令
3. 明确告知用户需要提供执行后的完整输出（建议重定向到文件：`python xxx.py 2>&1 | tee output.log`）

### 第3步：修复循环

进入循环，每轮执行以下步骤：

```
一轮修复循环：
1. 分析错误输出
2. 定位根因（使用 systematic-debugging 技能辅助分析）
3. 修改代码（一次只改一个问题的修复）
4. 如果是完全自主模式 → 重新执行验证
5. 如果是半自主模式 → 准备新的执行命令让用户运行
6. 检查是否成功：
   - 成功 → 退出循环，提交变更，告知用户
   - 失败 → 记录本轮失败原因，进入下一轮
```

### 第4步：停止条件

满足以下**任一**条件时停止循环：

1. **修复成功** —— 所有目标测试通过 或 用户确认问题解决
2. **达到最大轮数** —— 连续修复 5 轮未成功（计数不含初始诊断轮）。停下后向用户总结：
   - 尝试了哪些修复
   - 每轮的结果
   - 为什么还没解决
   - 下一步建议
3. **需要新依赖/权限** —— 需要安装新包、改系统配置、需要管理员权限等。停下询问用户。
4. **问题超出范围** —— 修复涉及完全不同的模块或需要架构性决策。停下咨询用户。

### 第5步：提交通知

修复成功后：
1. 运行 Verification Gate（typecheck + 相关测试 + lint）
2. 提交 commit（按照 AGENTS.md 的 auto commit 规则）
3. 向用户总结：
   - 根因
   - 修改的文件和内容
   - 验证结果
   - 如果半自主模式下用户尚未验证最终效果，告知用户如何验证

---

## 内存管理

每轮修复的关键发现（根因、失败尝试、有效方案）必须保存到 agentmemory：
- 根因 → `type: bug`
- 架构决策 → `type: architecture`
- 项目模式/约定 → `type: pattern`

---

## 规则

1. **一次只修一个问题。** 不要同时改多个不相关的错误。如果输出包含多个错误，逐个修复，每轮解决一个。
2. **没有证据就不要猜。** 必须先执行并获取输出，再分析根因。禁止根据已知信息猜测新的错误原因而不执行验证。
3. **每一次修复必须是可验证的。** 完全自主模式必须通过重新执行来验证。半自主模式必须明确告诉用户要验证什么。
4. **不要为了速度跳过分析。** 每轮都要花时间做根因分析（而不是随机尝试），分析后写入 agentmemory。
5. **诊断优先于修复。** 如果不确定根因，先添加诊断输出再执行，而不是盲目修。
